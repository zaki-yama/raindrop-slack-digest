## 1. [How's Linear so fast? A technical breakdown](<https://performance.dev/how-is-linear-so-fast-a-technical-breakdown>)

performance.dev

Linear の操作が数ミリ秒で終わる理由を、外部から観察した著者(Linear 社員ではない)が解説した記事。ブラウザ内DBと同期エンジン、初回ロードの最適化、キーボード中心の設計、軽いアニメーションといった多数の判断の積み重ねが速さを生んでいると述べている。SWR や TanStack Query の楽観的更新で近い体験を得る方法にも触れている。

- UIが読むDBはブラウザの IndexedDB にあり、変更はまずメモリ上の MobX に反映され、後からサーバーへ同期されるためスピナーが不要になる。
- ビルドはParcelからRollup、Vite、Rolldownへ移行し、最新ブラウザのみ対象にした。約21MBのJSを数百のチャンクに分割し、modulepreloadで並列取得する。
- Service Worker が約1,200のアセットをバックグラウンドでキャッシュし、オフラインでも閲覧や編集ができる。
- 初期HTMLにCSSと小さなJSをインライン化してアプリシェルを即描画し、認証はローカルデータがあればまず描画して、失敗時のみ401でログインへ戻す。
- MobXでプロパティ単位に再描画し、コマンドパレットはローカルのオブジェクトプール検索で動く。アニメーションは transform と opacity 中心で、表示は即時、消える時だけ短くフェードする。

**🏷️ タグ:** `#perf`

## 2. [Intent to prototype: WebAssembly Component Model](<https://groups.google.com/a/mozilla.org/g/dev-platform/c/sWKxAqONNRA/m/Iqy4BD86AgAJ>)

groups.google.com

MozillaのFirefox開発者向けMLに投稿された、WebAssembly Component Modelのプロトタイプ実装の意図表明です。Component Modelは、高水準の型によりWeb APIのimportやJS等から使えるAPIのexportを可能にする提案で、W3CのWebAssembly CG/WGで議論されています。性能向上と開発体験の簡素化を目指して実験するとしています。

- WebAssembly Component Modelは、W3CのWebAssembly CG/WGで議論されている提案である。
- wasmコンポーネントは高水準の型を持ち、Web APIのimportと、JS等から使えるAPIのexportができる。
- 内部実装はwasmモジュールと、値の受け渡しに使うABIで構成される。
- Webページの性能向上と、wasm利用時の開発者体験の簡素化を目的に実験する。
- 全プラットフォーム対象で、Preferenceは javascript.options.wasm_components。
- 他ブラウザはBlinkが評価中、WebKitは立場なし。WPTはまだなく、プロトタイプ中に作成を始めたいとしている。

**🏷️ タグ:** `#Frontend`

## 3. [Vercel Labs Ships scriptc, a TypeScript-to-Native Compiler That Leaves the JavaScript Engine Behind](<https://www.infoq.com/news/2026/09/vercel-scriptc-node/?via=dailydev>)

infoq.com

Vercel LabsがApache 2.0の実験的コンパイラscriptcを公開した。通常のTypeScriptを、NodeやV8、JavaScriptエンジンを含まない小さなネイティブ実行ファイルにする。ベンチマークでは起動とメモリで優位な一方、計算性能や既存プロジェクトの互換性、継続性には懸念が出ている。

- TypeScript公式コンパイラで解析と型検査を行い、型付きIRを経てC、LLVM IR、ネイティブ実行ファイル、WASI Preview 1のWebAssemblyを出力する。
- 構文は静的コンパイル、--dynamic指定時に組み込みquickjs-ng(約620KB)で動的実行、またはSCコード付きでコンパイル拒否、の3層に分かれる。
- scriptc 0.0.16のベンチマークでは起動中央値が1.78msで、Bunは21.29ms、Nodeは61.78msだった。アイドルメモリは1.9MiB。
- Honoは--dynamicが必要でサーバーの62%がQuickJSで動き、スループットは18.4k rpsとBunの70.5k rpsを大きく下回った。
- HNでは計算がNode 24比で約7.5倍遅い報告や、手元のプロジェクトで多数のエラーが出る報告があった。Vercelのzerolangのように開発が止まる懸念も挙がった。
- 文字列はUTF-8、メモリは参照カウント方式など、Nodeとの意図的な差異がある。Node.js 24以上が必要で、実験的と明記されている。

**🏷️ タグ:** `#Frontend`

## 4. [vercel-labs/scriptc: TypeScript-to-Native Compiler](<https://github.com/vercel-labs/scriptc>)

github.com

scriptcは、TypeScript compilerで解析と型チェックを行い、TypeScript/JavaScriptをネイティブ実行ファイルやWebAssemblyへコンパイルする実験的ツールだ。静的ビルドにはNodeやJSエンジンを含めず、静的化できないコードは診断で報告する。npmパッケージやany型のコードには--dynamicでquickjs-ngを埋め込む。

- typed IR、読みやすいC、LLVM IR、asm、obj、実行ファイル、Wasmを--emitなどで出力でき、成果物は.scriptc/に蓄積される。
- 静的ビルドは小さなネイティブランタイムを含むが、NodeやJavaScriptエンジンは含まない。生成した実行ファイルもNodeを必要としない。
- node:httpなど対応するNode APIはネイティブランタイムにコンパイルされ、scriptc coverageで静的化できる範囲を確認できる。
- WASI Preview 1向けのビルドにはZigが必要。ネットワーク、子プロセス、シグナル、ファイル監視はSC3002で失敗する。
- テストコーパスは各プログラムをNodeとネイティブバイナリで実行し、stdout、stderr、終了コードをバイト単位で比較する。ASanと参照カウント監査も実行する。

**🏷️ タグ:** `#Frontend`

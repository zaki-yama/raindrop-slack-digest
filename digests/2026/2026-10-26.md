## 1. [Claudeが実装したE2Eテストをレビューするツールを自作してみた - エムスリーテックブログ](<https://www.m3tech.blog/entry/2026/10/14/133340>)

m3tech.blog

エムスリーQAチームが、Claudeで実装したPlaywrightのE2Eテストの手順や操作対象が正しいかを人がレビューするためのツールを自作した。操作直前に対象要素をハイライトしたスクリーンショットを撮り、APIレスポンスやファイル、メールなど画面のない検証もテスト手順に紐づけて表示する。CIの失敗調査にはTrace Viewerを使う。

- Claudeのテストは成功しても手順や操作対象が誤っていることがあり、人のチェックが必要。
- Trace Viewerは1ステップずつ確認する必要があり、画面を伴わない検証も見づらいため自作した。
- Locator/Pageの操作とアサーションをラップし、実行直前に対象をハイライトしたスクリーンショットを撮影し、API名を自然言語ラベルに変換する。
- アサーションのリトライ時は検証後も撮影し、要素は block: 'center' で中央にスクロールし、存在しない要素はフルページ撮影でcount()が0ならスクロールをスキップする。
- page.gotoは最大3秒通信の落ち着きを待って撮影し、API・ファイル・メールの検証は専用ヘルパー関数で表示する。
- 撮影コストとDOM挿入の副作用があるため環境変数指定時のみ動作し、CI失敗調査はTrace Viewerを使う。Page Objectのリファクタリング前後の比較にも利用している。

## 3. [1Password、AIエージェント用パスワード「1Password for Agents」発表](<https://ai.watch.impress.co.jp/docs/news/2150830.html>)

ai.watch.impress.co.jp

1Passwordは、AIエージェントにパスワードを公開せずにアクセスさせる「1Password for Agents」を発表した。エージェントのリクエストをユーザーが承認すると、1Passwordが認証情報を宛先サイトに直接自動入力する方式である。複数のAIサービスと連携済みで、他のサービスも順次対応予定とされている。

- エージェントはユーザーの保管庫から認証情報の使用をリクエストし、承認後に1Passwordが宛先サイトへ直接自動入力する。
- AIエージェントは保管庫の認証情報そのものにはアクセスできない。
- プロンプトから実際のアクセスまで、エージェントがアクセスできるタイミングと権限を制御できる。
- 現在はMetaのMuse、AnthropicのClaude Duet、OpenAIのChatGPT Workとdots、SpaceXSIのGrok Bot、TownのTownieと連携している。
- 近日中にInstinct、Browserbase、Browser Use、Dana、KERNEL、Perplexity、Ramp、Tomo、Wajoとも連携予定。

## 4. [eMudhra のインシデントは Web にとって何を意味するのか | blog.jxck.io](<https://blog.jxck.io/entries/2026-10-25/emudhra.html>)

blog.jxck.io

eMudhra のキーセレモニーで不備があり、中間 CA の鍵が実質 1 byte の弱い鍵になっていた。筆者は、これを Web の信頼の根幹であるトラストアンカーが崩れた事態として論じている。Cross Root の問題や個別の証明書ストアなど対応の難しさ、eMudhra が TLS 事業から撤退した件、CA に求める責任も述べている。

- スクリプトのバグで P-384 の鍵の上位 47 byte が 0 になり、実質 1 byte の弱い鍵が中間 CA に採用された。
- 256 回ほどの総当たりで鍵を復元でき、任意ドメインの正規の証明書を複製できる。これは CA の秘密鍵漏洩と実質同じだと筆者は見ている。
- ブラウザは CT Log の SCT 要件でリスクが下がるが、完全な対策には Cross Root である Sectigo 経由の経路を失効で塞ぐ必要がある。
- Electron アプリや curl、cacert.pem など独自に証明書ストアを持つ実装は個別更新が必要。暫定策として VPN の利用なども挙げている。
- eMudhra は SNS での批判を理由に、反省を示さないまま TLS 証明書事業から撤退を発表した。筆者はこれを強く批判している。

## 5. [ghtkn が access token の自動更新をサポート](<https://zenn.dev/shunsuke_suzuki/articles/ghtkn-refresh-token>)

zenn.dev

GitHub App の User Access Token を生成する CLI「ghtkn」が、v0.3.4 から refresh token による access token の自動更新に対応した。記事では設定手順、agent の暗号化や lock などの安全対策、ホストの agent をコンテナから使う方法を説明している。

- 自動更新は macOS と Linux の agent backend のみ対応で、Windows、keyring backend、text backend は意図的に非対応。
- 利用には ghtkn と SDK 依存ツールの更新、backend を agent に変更、agent 起動、ghtkn agent unlock --enable-refresh の実行が必要。
- アプリごとに一度 device flow を行えば以後は自動更新され、ghtkn auth も内部で更新を行う。
- refresh token の有効期限は半年。agent は未使用のトークンを24時間ごとに確認し、デフォルト1週間で削除する。
- refresh token は AES-256-GCM で暗号化し、OS Keyring は使わず、取得用のコマンドや API も用意しない。更新失敗時は漏洩の可能性を警告する。
- コンテナ内ではなくホストで agent を動かし、socket を bind mount(macOS は SSH 転送経由)する方が安全。コンテナには access token しか渡らない。

azukiazusa.dev

pstack は poteto 氏によるエージェントスキル集で、コード量より品質を重視し、少ないコードで目的を達成することを目指す。記事では開発原則と対応するスキル、Claude Code での導入手順を説明し、実際にバグ修正とリポジトリ説明を依頼して動作を確認している。

- /poteto-mode が依頼に応じて Bug fix などのプレイブックを選び、作業手順の中で必要なスキルを呼び出す。
- how は既存コードの動きを調べて理解を促し、architect は型や境界を先に描き複数案を比較してから実装に進む。
- Laziness Protocol は最小限の差分を、Prove It Works はコンパイル成功や自己申告でなく実際の成果物での確認を求める。
- interrogate は複数モデルのレビューを、対応すべき問題・提案・記録・却下に分類する。自動適用はしない。
- Claude Code では /plugin で導入し /setup-pstack でモデルと推論予算を設定する。設定は ~/.claude/rules/pstack-models.md に保存される。
- 500エラーの試行では、原因が slug 空文字によるキー重複とハイドレーション失敗と判明し、データ修正と生成バグの是正が提案された。

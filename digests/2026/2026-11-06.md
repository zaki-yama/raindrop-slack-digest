## 2. [Building agents: When to fold subagents into your main agent loop](<https://claude.com/ja/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop>)

claude.com

Claude Platform で作る多数のサブエージェントのうち、メインのエージェントループに統合した方がよいものを見極める方法を解説する記事。大組織でありがちな組織図そのままのサブエージェント乱立の弊害と、プログレッシブ・ディスクロージャーを使う単一ループ設計、段階的な移行手順、移行を支援するツール群を紹介している。

- 複数の企業導入の比較で、スキル付き単一エージェントは品質で勝ることが多く、コストや遅延も下がることが多かった。
- 大組織ではコンテキスト管理、サブエージェント乱立、Frankenprompt、局所的な eval、遅延が問題になる。ある顧客では単一ループの方が実行時間が約2倍速かった。
- サブエージェントを残す条件は、コンテキスト肥大による性能低下、新しいコンテキストでの並列作業、ツール選択の困難や指示の衝突の3つ。
- 移行は eval 作成から始める。密結合なものを統合し、サブエージェントのツール化を経て、プロンプトをスキルに、API 呼び出しを MCP ツールに置き換える。
- 比較では最終スコアだけでなく、結果が変わったタスクを見る。各タスクは複数回実行する。支援ツールとして /claude-api の build-eval、prompt-audit、hillclimb、cost-optimize がある。

## 3. [キャッシュコヒーレンスの仕組みとパフォーマンスへの影響 - 30歳からのプログラミング](<https://numb86-tech.hatenablog.com/entry/2026/11/05/183112>)

numb86-tech.hatenablog.com

CPUのキャッシュメモリ、Dirtyマーク、マルチプロセッサ環境で整合性を保つキャッシュコヒーレンスの仕組みを説明する記事。Rustで書いた2つのプログラムをUbuntu上で実行し、コヒーレンス処理による性能低下をperf statのイベント数で確認している。

- キャッシュはキャッシュライン(検証機では64バイト)単位で管理され、書き込み済みのラインにはDirtyマークが付いて、後でメインメモリに反映される。
- キャッシュコヒーレンスは2つのルールで成り立つ。書き込み前に他CPUのコピーを無効化し、無効化済みデータの読み出し時は他CPUのキャッシュから取得する。
- ping-pongのプログラムでは、同一物理コアの論理コア0と4(mode a)が1周39.75ns、別物理コアの0と1(mode b)が154.92nsだった。
- perf statでは、mode bでxsnp_fwdとdemand_rfoがそれぞれ約1000万回(ループ回数とほぼ同数)に達し、mode aはほぼ0だった。
- フォルスシェアリングのプログラムでは、変数が同じキャッシュラインに入るsameが1.16ns/回、別ラインのseparateが0.20ns/回で、5倍以上の差が出た。

## 4. [PDD Kit](<https://githubnext.com/projects/pdd-kit/>)

githubnext.com

GitHub NextとMicrosoft Researchの研究プロトタイプPDD Kitは、コーディングエージェントが書いたコードの行単位レビューが難しい問題に対し、人の判断を意図と仕様の承認に集中させる。コードが仕様を満たすことはRust向け証明言語Verusで形式検証し、証明できない部分はテストで補う。Pet Storeのログイン処理を例に、依頼から仕様、証明、PRまでの流れを示している。

- エージェントのコードには、計画が拘束力を持たない、テストが作られたものしか見ない、行単位レビューが破綻する、弱い仕様で通るvibe verificationという4つの問題がある。
- PDD Kitは決定カードで人に質問して意図を固め、形式仕様(Verus)と、テストで確認する非形式仕様に分けて記録する。
- ログインの2文の依頼は、「正しいパスワードなら必ずトークンが得られる」という逆方向の仕様も含む8節のensuresになった。
- bcrypt、SQLite、JWT署名などは信頼境界(TCB)として6つの契約に分け、人が承認し、それぞれにテストを付ける。
- 仕様が空疎でないかを節ごとにバグを仕込むミューテーション検査で確かめ、PRは検証済み・信頼・限界を示すレシートとして使う。
- 現状はRustのみ対応で、証明には労力がかかる。完了性や速度、人の判断が要る事項は証明の対象外。

**🏷️ タグ:** `#LLM`

## 6. [GitHub Next、AI生成コードが仕様を満たすことを証明する「PDD Kit」を紹介 | gihyo.jp](<https://gihyo.jp/article/2026/11/pdd-kit>)

gihyo.jp

GitHub NextがMicrosoft Researchと共同開発するPDD Kitを紹介した。対話で曖昧な要求をVerusの仕様に落とし込み、AIエージェントが生成したRustコードが仕様を満たすことを証明で確かめる。Pet Storeのログイン処理を例に、仕様作成から証明、テスト、PR作成までの流れが説明されている。

- PDD KitはGitHub NextのWebアプリChopin内で動き、計画づくりの対話から機械検証可能な仕様を作る。
- ログイン処理の例では、「正しいパスワードなら必ずトークン発行」も要求に加え、最終的に8つの条件の仕様になった。
- 仕様の各条件に違反するバグを作業用コピーに一つずつ入れ、Verusが検出することで仕様が緩すぎないか確かめる。
- DB検索やbcryptなど外部ライブラリは証明対象外で、前提として開発者が承認し、その前提を確かめるテストも計画する。
- 保証は仕様の範囲に限られ、処理の完了や応答時間は保証しない。マージ後はVerus検証とテストをCIに組み込む。

## 7. [\[CSS\] ボタンのcursorはpointerにすべきか | 零弐壱蜂](<https://b.0218.jp/202611030121.html>)

b.0218.jp

ボタンに cursor: pointer を当てるべきかを、CSS仕様、OSのガイドライン、CSSWGの議論、各フレームワークの既定から検討した記事。結論として、カーソルに頼らず見た目でボタンと分かるようにしたうえで、迷ったら pointer にそろえ、すでに default で統一しているなら変えないとしている。pointer と default それぞれにそろえる場合のCSS例も示している。

- 仕様は pointer を「リンクを示すポインタ」と定義するが、開発者がリンク以外に使うことは縛っていない。
- default 派はOSとの一貫性を、pointer 派はWeb上での一貫性を重視しており、対立点はどの一貫性を守るかにある。
- CSSWGは2026年10月21日、button や select などを pointer、無効なコントロールを not-allowed とする規則を決議したが、仕様にはまだ入っていない。
- Bootstrap 5.3は pointer を維持し、Tailwind v4とshadcn/ui(Tailwind v4版)は default に変更しており、フレームワークの既定も割れている。
- 実装例では summary や role="button" の扱い、disabled属性と aria-disabled の両方を拾う点に注意が必要で、Chrome 153でのみ計算値を確認している。

**🏷️ タグ:** `#Frontend`

## 8. [cloudflare/security-audit-skill: A coding-agent skill for multi-phase security audits with independently verified, machine-readable findings](<https://github.com/cloudflare/security-audit-skill>)

github.com

CloudflareのOSSスキル「security-audit-skill」は、コーディングエージェントを使ってリポジトリのセキュリティ監査を6フェーズで進める。探索担当と検証担当を別々の隔離エージェントにし、結果をJSONスキーマで検証した上でレポートを生成する。Cloudflareの脆弱性発見ハーネスの出発点となったスキルである。

- 6フェーズは、偵察、網羅性主導の探索、候補の検証、構造化出力、独立した記録検証、レポート生成からなる。
- 発見の判定は3種類。confirmedは完全なソーストレースと観測結果があり、needs_validationは未解決の事実を明示して重大度を付けず、rejectedは反証された候補である。
- findings.jsonとcoverage-ledger.jsonは、依存なしのNode.js製バリデータで各フェーズ後に検証する。
- メモリ安全性、Web認証、サプライチェーン、クラウドなど、対象別の攻撃クラス集を用意している。
- 対象コードの実行にはOS強制のサンドボックスが必須。ネットワーク遮断、環境変数の許可リスト化、リソース制限が条件で、満たさなければneeds_validationにとどめる。
- 複数回の実行は結果が積み上がる。前回の台帳や結果を使って未カバー部分を狙う。

## 9. [A fully programmable secure web gateway](<https://blog.cloudflare.com/programmable-gateway-dlp?via=dailydev>)

blog.cloudflare.com

Cloudflare が Gateway と DLP を Workers と統合し、ポリシー評価の途中で独自コードを実行できるようにした。新しい Forward アクション、Custom Functions、DLP の検証関数を紹介している。Gateway と Workers は同じマシン上で動くため、ネットワークホップは発生しないと説明している。

- Forward アクションは、許可された HTTP トラフィックのうち最初に一致したルールの Worker に送り、ヘッダーや本文、レスポンスを加工できる。公開ベータで提供中。
- Custom Functions は Worker が型付きの値を返し、ネットワークや HTTP のルール条件のセレクタとして使える。年内提供予定。
- Custom Functions は失敗時のフォールバックを関数ごとに設定でき、既定値が契約上必須。
- 用途の例は、正当性の入力を求める中間ページ、JWT からのヘッダー注入、ファイルの保存や検査、Slack などへのリアルタイム通知。
- DLP の検証関数は今日から使え、一致時に Worker で検証してから判定できる。課金は通常の Worker リクエストと同じで、Workers Free にも実行時間と日次リクエストの上限がある。

**🏷️ タグ:** `#Frontend`

## 10. [プルリクエストのリスクを判定する仕組み - newmo 技術ブログ](<https://tech.newmo.me/entry/2026/10/27/100000>)

tech.newmo.me

newmo のモノレポで運用している、AI が PR を読んで安全と判断したものを bot が承認する「riskjudge」の技術解説。判定を機械ゲート、LLM ゲート、複数回判定、決定式のレイヤに分け、見えない変更や重要領域は人に回す設計を紹介している。約 2 か月の運用で判定と結果を突き合わせた数値や、ゲートごとの効き方も述べている。

- PR ごとに approve か needs_human を返し、全レイヤは AND でつながる。安い判定から順に評価し、引っかかった時点で後ろは評価しない。
- 機械ゲートは認証・決済・インフラなどのパスを LLM の前に止める。生成物は .gitattributes の linguist-generated で判別して LLM の入力から外す。
- LLM とは JSON の構造化出力でやりとりし、業務ロジックの変更は「振る舞いが変わるか」「単純で定型的か」の 2 段の問いで判断する。prompt injection も前提に、判定基準は差分のフェンスより前に置く。
- 重要領域と 1,000 行超の PR は同じ判定を 3 回行い、1 票でも懸念があれば懸念ありとする OR で集約する。人のコメント率は PR の大きさと強く相関し、1,000 行超では 60% だった。
- approve した PR の不具合原因率は needs_human の約半分。一方、「業務ロジックの変更」で止めた PR は approve との差が小さく、止めすぎだった。見逃しは差分の外を読まないと分からないものが多かった。
